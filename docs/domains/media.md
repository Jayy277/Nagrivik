# Media Domain & Visual Evidence Architecture

## 1. Domain Purpose

Visual evidence is fundamental to civic accountability. When citizens report civic issues (such as potholes, open garbage dumps, water pipeline bursts, or non-functioning streetlights), attaching photographs provides concrete proof of the problem and enables municipal departments to assess severity, dispatch the right workforce, and verify work completion.

The **Media Domain** provides the authoritative metadata model for files associated with civic issues in Nagrivic.

---

## 2. Storage Architecture: Metadata vs. Object Storage

A core architectural invariant of Nagrivic is:

> [!IMPORTANT]
> **PostgreSQL does NOT store binary image files.**
> PostgreSQL stores **only structured metadata** (`storage_key`, `content_type`, `file_size_bytes`, `media_type`, `display_order`, timestamps).
> The actual binary image assets will be stored in private, S3-compatible object storage (e.g., Cloudflare R2, MinIO, or AWS S3).

```
Mobile App / Web Client
       │
       ▼ (Future Upload API)
Nagrivic Backend
       │
       ├── Writes Metadata ──────────► PostgreSQL (`media` table)
       │
       └── Streams / Presigns Upload ► S3-Compatible Object Storage
```

## 3. Database Schema (`media`)

Defined in Flyway migration `V9__create_media_table.sql`:

```sql
CREATE TABLE media (
    id UUID PRIMARY KEY,
    issue_id UUID NOT NULL,
    storage_key VARCHAR(512) NOT NULL,
    original_filename VARCHAR(255),
    content_type VARCHAR(128) NOT NULL,
    file_size_bytes BIGINT NOT NULL,
    media_type VARCHAR(32) NOT NULL DEFAULT 'IMAGE',
    display_order INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT fk_media_issue_id FOREIGN KEY (issue_id) REFERENCES issues(id) ON DELETE CASCADE,
    CONSTRAINT uq_media_storage_key UNIQUE (storage_key),
    CONSTRAINT chk_media_file_size_positive CHECK (file_size_bytes >= 0),
    CONSTRAINT chk_media_display_order_non_negative CHECK (display_order >= 0)
);

CREATE INDEX idx_media_issue_id ON media(issue_id);
CREATE INDEX idx_media_issue_display_order ON media(issue_id, display_order ASC);
```

### Key Schema Fields
| Field | Column | Type | Constraints | Description |
|---|---|---|---|---|
| `id` | `id` | `UUID` | `PRIMARY KEY` | Globally unique identifier (UUIDv4). |
| `issue` | `issue_id` | `UUID` | `NOT NULL`, `FK` | References `issues(id)` with `ON DELETE CASCADE`. |
| `storageKey` | `storage_key` | `VARCHAR(512)` | `NOT NULL`, `UNIQUE` | Internal server-generated object path (e.g. `issues/{issueId}/{uuid}.jpg`). |
| `originalFilename` | `original_filename` | `VARCHAR(255)` | Nullable | Original filename from user device, stored strictly for display metadata. |
| `contentType` | `content_type` | `VARCHAR(128)` | `NOT NULL` | MIME type (e.g. `image/jpeg`, `image/png`, `image/webp`). |
| `fileSizeBytes` | `file_size_bytes` | `BIGINT` | `NOT NULL`, `>= 0` | Size of the file in bytes. |
| `mediaType` | `media_type` | `VARCHAR(32)` | `NOT NULL`, default `'IMAGE'` | Controlled application media type enum. |
| `displayOrder` | `display_order` | `INT` | `NOT NULL`, default `0`, `>= 0` | Presentation sequence for multi-image issue views. |
| `createdAt` | `created_at` | `TIMESTAMPTZ` | `NOT NULL` | UTC creation timestamp. |

## 4. Storage Key Principles

1. **Server-Generated**: Clients **never** supply or dictate the `storage_key`. It is deterministically generated by the backend service.
2. **Path Traversal Protection**: Clients cannot specify storage paths, eliminating directory traversal vulnerabilities (e.g. `../../etc/passwd`).
3. **No Collision**: Keys incorporate UUIDs and parent entity identifiers (`issues/{issueId}/{mediaId}.{ext}`).
4. **Information Hiding**: Internal storage keys and bucket names are **never** leaked to public client DTOs (`MediaResponse`).

---

## 5. Referential Integrity & Delete Behavior

- **Cascade on Parent Deletion (`ON DELETE CASCADE`)**: Media records represent visual evidence that belongs strictly to a specific civic issue. If an issue is ever deleted, its associated media metadata records are cascaded and purged automatically, preventing orphaned metadata rows.
- **Ordered Presentation**: Multi-image queries are indexed by `(issue_id, display_order ASC)`, enabling fast sequential image galleries in mobile and web clients.

---

## 6. Security Principles (For Future Upload Service)

When file uploading is implemented in a future task, the upload pipeline must adhere to the following mandatory security rules:
1. **Magic Bytes Validation**: Do not trust the client-supplied `Content-Type` header or file extension. Verify real file signatures (magic bytes) for JPEG, PNG, and WebP.
2. **Enforce Size Limits**: Strict byte size limits (e.g., max 10MB per image) enforced prior to streaming.
3. **Prevent Executable Uploads**: Only allow safe raster image formats. Disallow SVG, HTML, scripts, or executables.
4. **Private Storage by Default**: Media bucket must be private with no public write access. Reads must be controlled via CDN or short-lived pre-signed URLs.

---

## 7. Privacy Considerations

Citizen-uploaded photos of public spaces may unintentionally capture sensitive personal details:
- **People's Faces**: Incidental pedestrians.
- **Vehicle License Plates**: Private vehicles parked or driving near civic problems.
- **Personal Documents**: Mail, notices, or residential house numbers.
- **Stripping EXIF Metadata**: Future upload pipelines must strip EXIF metadata (especially embedded GPS coordinates and device identifiers). The authoritative location of the issue is managed by the **Location Domain** (`issues.location_id`), not untrusted client EXIF tags.

---

## 8. Deferred Features (Strict Boundaries)

The following features are intentionally out of scope for Task 8 and deferred to future tasks:
- S3 / MinIO / Cloudflare R2 SDK integrations
- Multipart upload and file streaming APIs (`POST /api/issues/{id}/media`)
- Pre-signed upload and download URLs
- Image compression, thumbnail generation, and resizing
- Mobile camera and gallery pickers
- AI image moderation or automated blurring
